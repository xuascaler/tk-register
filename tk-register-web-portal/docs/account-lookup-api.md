# Account Lookup API

## Overview

The Account Lookup API returns the saved status, cumulative usage and latest collection result for one Claude account owned by the authenticated TK Register user.

| Property | Value |
| --- | --- |
| Method | `GET` |
| Path | `/tk-register/api/v1/vendors/tk-register-0/claude/accounts/lookup` |
| Authentication | Personal TK Register API token in `Authorization: Bearer <token>` |
| Required scope | `accounts:read` |
| Request parameters | `username` and `account`, in the query string |
| Request body | None |
| Response format | JSON, using the TK Register `success` / `data` envelope |
| Rate limit | 60 lookup requests per minute per authenticated user |
| Data source | Saved TK Register account data and collection snapshots |

This is a read endpoint. A lookup does not submit an account, sign in to the supplier website, refresh supplier data or start a collection run. It returns the same saved account metrics used by **My account → Accounts**.

For how snapshots are collected and how an administrator changes the interval, see [Account usage collection](account-sync.md). For submitting an account, see [User API tokens and external APIs](../README.md#user-api-tokens-and-external-apis).

## Authentication and ownership

Generate a token under **My account → Account settings → API token**. Send the full token in a single `Authorization` header:

```http
Authorization: Bearer tkr_<your-personal-token>
Accept: application/json
```

A browser login cookie and a CSRF token are not required. A supplier Bearer credential cannot be used in place of the personal TK Register token.

Tokens generated or regenerated by TK Register have both `claude:submit` and `accounts:read` access. A one-time upgrade migration adds `accounts:read` to existing tokens with the original `claude:submit` scope. Their token value remains unchanged, so regeneration is not required. The migration is not reapplied on later restarts and does not overwrite subsequent scope changes. This does not reactivate revoked, expired or otherwise invalid tokens.

The token always identifies the requesting user. The `username` query parameter must identify that same user; it does not let the caller choose another user's permissions. An administrator's personal token is also restricted to the administrator's own submitted accounts. Access to other users' accounts through the administrator website does not extend the personal token's permissions.

The server uses the same `404 ACCOUNT_NOT_FOUND` response for a missing account and an account outside the token owner's scope, including a `username` that does not match the token owner.

## Request

```http
GET /tk-register/api/v1/vendors/tk-register-0/claude/accounts/lookup?username=member%40example.com&account=claude.user%40example.com
Authorization: Bearer tkr_<your-personal-token>
Accept: application/json
```

### Query parameters

| Parameter | Type | Required | Meaning |
| --- | --- | --- | --- |
| `username` | string | Yes | The TK Register user's email address. Must match the personal token's owner. |
| `account` | string | Yes | The submitted Claude account's login ID or email address. This can differ from `username`. |

Both parameters are matched by their complete normalized values: surrounding whitespace is trimmed and case is normalized. The endpoint is an exact lookup, not a substring search. It does not accept wildcard or pagination parameters.

Rules:

- Supply `username` and `account` exactly once each. Missing, empty, duplicate or unsupported query parameters return `400 INVALID_REQUEST`.
- Do not send a JSON object, form data or any other request body with this `GET` request.
- `account` is limited to 254 bytes after trimming and must not contain internal whitespace or control characters, including Unicode whitespace and control characters.
- The vendor and Claude account family are fixed by the URL. Do not add `provider`, `model`, `account_type`, vendor credentials or proxy parameters.
- URL-encode both parameter values. In particular, an email address containing `+` must preserve that character as `%2B`.

### cURL example

The following example assumes that `TK_REGISTER_API_TOKEN` already contains your personal token. Replace the two example addresses with your TK Register login email and the submitted account identifier.

```sh
TK_REGISTER_BASE_URL='https://47.110.71.25:8443'

curl --silent --show-error --include --get \
  "${TK_REGISTER_BASE_URL}/tk-register/api/v1/vendors/tk-register-0/claude/accounts/lookup" \
  --header "Authorization: Bearer ${TK_REGISTER_API_TOKEN}" \
  --header 'Accept: application/json' \
  --data-urlencode 'username=member@example.com' \
  --data-urlencode 'account=claude.user@example.com'
```

`--get` puts the encoded values in the query string; it does not create a request body. `Content-Type: application/json` is unnecessary because there is no body. `--include` prints the HTTP status and headers, including `Retry-After` when the request is rate-limited.

Use the deployment's trusted certificate or provide its CA with `--cacert /path/to/ca.pem`. If testing the existing IP-based deployment with its self-signed certificate, `--insecure` (`-k`) can be added explicitly; it disables certificate verification for that test request. It is not required by the API itself.

## Successful response

HTTP `200 OK` means that the owned account was found and its saved data was read successfully. It does not imply that the supplier account is active or that the latest collection attempt succeeded.

### Account fields

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | string | Stable local account record ID. Distinct from a submission ID and both remote IDs. |
| `username` | string | The account owner's TK Register login email. |
| `account` | string | Stored submitted account identifier. Matching is normalized even if the stored display value preserves its original case. |
| `vendor` | string | Always `tk-register-0` for this endpoint. |
| `plan` | string | Plan associated with the saved account. |
| `remote_id` | string or null | ID returned by the supplier account creation endpoint, when available. |
| `platform_account_id` | string or null | Supplier platform account ID, when available. It is separate from `remote_id`. |
| `submission_status` | string | Latest submission attempt's saved state, such as `accepted`, `running`, `failed` or `unknown`. This is not the supplier account status. |
| `snapshot` | object or null | Latest successfully saved snapshot for the account's current lifetime. `null` if none is available. |
| `last_success_at` | RFC3339 string or null | Most recent successful collection time. Does not indicate that the supplier account is healthy. |
| `last_attempt_at` | RFC3339 string or null | Most recent collection attempt, whether successful or unsuccessful. |
| `last_error` | string or null | Sanitized collection failure message, or `null` when no failure is recorded. |
| `interval_hours` | integer | Current configured automatic collection interval in hours. The default is 2; administrators can change it. This field alone does not indicate that scheduled collection is enabled. |

### Snapshot fields

| Field | Type | Meaning |
| --- | --- | --- |
| `id` | string | Snapshot record ID. |
| `account_id` | string | Associated stable local account record ID; matches the response's top-level account `id`. |
| `snapshot_date` | `YYYY-MM-DD` string | Collection date in the configured collection timezone. |
| `collected_at` | RFC3339 string | Actual time at which this snapshot was collected. |
| `source_updated_at` | RFC3339 string or null | Reliable upstream usage-update time, if supplied. Otherwise `null`. |
| `account_status` | string or null | Normalized supplier status at collection time, for example `active`, `offline`, `banned`, `pending`, `limited` or `unknown`. |
| `input_tokens_total` | number or null | Cumulative input-token counter. |
| `output_tokens_total` | number or null | Cumulative output-token counter. |
| `cost_total` | number or null | Original cumulative spending in the accompanying `currency`, already normalized from supplier micro-units into currency units. Retained unchanged for compatibility. |
| `currency` | string or null | Currency of the original `cost_total`, such as `CNY`. |
| `cost_total_usd` | number or null | Cumulative spending in USD, calculated as `cost_total / 7.2` when `currency` is `CNY`. Null when the original amount is unavailable or the currency is missing or not CNY. A known zero remains `0`. |
| `exchange_rate_cny_per_usd` | number | Fixed conversion rate, always `7.2`: CNY per USD. Present even when `cost_total_usd` is null. |
| `usage_5h_percent` | number or null | Usage percentage in the five-hour window, such as `15` for 15%. |
| `reset_5h_at` | RFC3339 string or null | Five-hour window reset time. |
| `usage_7d_percent` | number or null | Usage percentage in the seven-day window. |
| `reset_7d_at` | RFC3339 string or null | Seven-day window reset time. |
| `data_source` | string | Collection source; `website` for this supplier integration. |

`cost_total_usd` retains calculation precision in the API; clients can format it to two decimal places for display. Do not convert `cost_total_usd` again. The original `cost_total` and `currency` retain their previous meanings. This fixed rate applies to both latest and historical snapshot responses; it is not a live or date-specific exchange rate.

The response does not contain account passwords, `auth_json`, personal token values, supplier Bearer credentials or supplier website login credentials.

## Freshness and missing data

The response is a stored view, not a real-time supplier query. Use `last_success_at` and `snapshot.collected_at` to decide how current the data is. Repeating this API request does not make the underlying snapshot newer.

| Situation | Response behavior | Client presentation |
| --- | --- | --- |
| Collection succeeded | Saved `snapshot`; `last_error` is null | Display the values and successful collection time. |
| A later collection failed | Previous successful `snapshot` retained; `last_error` populated and `last_attempt_at` updated | Display retained values as last-known data and show their original update time. |
| Account exists but has no collected data | `snapshot: null`; individual collection times may also be null | Show unavailable data, such as `—`. Do not infer zero usage. |
| One metric is unavailable | That metric is null even when other snapshot fields have values | Show only available metrics. |
| Supplier explicitly returned zero | The numeric field is `0` | Show a known zero, such as `0%` or `USD 0.00`. |

A new accepted supplier identity or plan can start a new account lifetime. Older snapshots are retained internally but are not returned as the current lifetime's latest snapshot.

This endpoint returns one latest snapshot, not a historical time series or billing-period query. Cumulative token and spending totals must not be interpreted as usage since the previous request. Repeated results represent the same saved observation.

## Errors and retry behavior

Error responses use the TK Register envelope:

```json
{
  "success": false,
  "code": "ACCOUNT_NOT_FOUND",
  "message": "The account could not be found."
}
```

The example message is illustrative. Use the HTTP status and `code` for programmatic handling; do not depend on exact message wording.

| HTTP status | Code | Meaning and action |
| --- | --- | --- |
| `400` | `INVALID_REQUEST` | Invalid or missing query values, duplicate/unsupported parameters, or a request body. Correct the request before retrying. |
| `401` | `INVALID_API_TOKEN` | Missing, invalid, revoked or expired token, or a user that cannot authenticate. Supply an active token. |
| `403` | `INSUFFICIENT_SCOPE` | Token is valid but lacks `accounts:read`. Check its permissions. |
| `404` | `ACCOUNT_NOT_FOUND` | No matching owned Claude account, including a different owner's username/account. Check both exact identifiers and the token owner. |
| `405` | `METHOD_NOT_ALLOWED` | Use `GET` for this endpoint. |
| `429` | `RATE_LIMITED` | Per-user lookup limit reached. Wait for the supplied retry interval. |
| `503` | `UNAVAILABLE` | A required database or Redis service is temporarily unavailable. Retry after a delay. |

The lookup limit is **60 requests per minute per user**. Requests with another token for the same user share that user's limit. The submission API's separate limit is unchanged.

A rate-limited response includes `Retry-After` in seconds and a JSON `retry_after` value:

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/json
Retry-After: 17
```

```json
{
  "success": false,
  "code": "RATE_LIMITED",
  "message": "Please wait before trying again.",
  "retry_after": 17
}
```

Lookups can be retried after a transient network failure or `503`, because the endpoint does not create submissions or invoke supplier operations. Use backoff rather than a tight retry loop. A successful `200` response with a non-null `last_error` describes the saved collection result; it is not a failed lookup request, and repeatedly querying will not fix the collector.

## Integration checklist

1. Use the **TK Register user's email** for `username` and the **submitted Claude account** for `account`.
2. URL-encode both parameters and authenticate with that user's personal Bearer token.
3. Check the HTTP status and `success` before reading `data`.
4. Keep identifiers as strings; keep null values distinct from zero.
5. Show the last successful collection time alongside any displayed status or usage.
6. Treat `submission_status` and `snapshot.account_status` as separate states.
7. Respect `Retry-After`; use the configured collection interval to choose a sensible client polling cadence.
